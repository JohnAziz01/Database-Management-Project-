AutoRisk Bug Fix Report

We wrote an automated test suite for AutoRisk, our car-insurance pricing app (React, FastAPI, PostgreSQL). Testing found 23 bugs. This report shows what each bug was, how we fixed it, and how the tests prove it stays fixed.

How we tested

Tests run at three levels. Each check sits at the lowest level that can catch its bug, because lower levels are faster and easier to debug. Every test starts from the same seed data in a throwaway PostgreSQL database in Docker, so the tests never touch the real (Neon) database.

LevelToolTestsWhat it proves
Unitpytest44The premium formula: age bands, experience bands, power bands, risk levels, boundary values
API / integrationpytest + FastAPI TestClient + PostgreSQL153Every endpoint: status codes, returned data, validation, login and role checks
End-to-endpytest + Playwright (Chromium)35Real user flows in the browser: sign in, search, add a policyholder, get a quote

Workflow for every bug: reproduce it with a failing test, fix the code, watch the test pass, and keep the test as a regression test.

Four bugs worth showing

BUG-001CriticalFixed

The data needed no login

The React app hid pages from logged-out users, but the API answered anyone. A single request returned every customer's personal data.

Before: GET /api/policyholders, no token 
200 OK  [ {"first_name": "Jordan", "date_of_birth": "1990-04-12",
          "license_number": "D1234567", ...}, ... ]
After: every data router 
router = APIRouter(prefix="/api/policyholders",
    dependencies=[Depends(get_current_account)])
# no token -> 401 Unauthorized
BUG-010HighFixed

A quote could cost less than nothing

The quote endpoint accepted any number. A negative bonus-malus coefficient produced a negative yearly premium.

Before: bonus_malus_coefficient = -1 
200 OK  {"estimated_premium": -545.74, "risk_level": "Low"}
After: schemas.QuoteRequest 
bonus_malus_coefficient: float = Field(ge=0.5, le=3.5)
vehicle_power_kw: int = Field(ge=1, le=1000)
# -> 422 with a message naming the field
BUG-018MediumFixed

“[object Object]”

The API correctly rejected a bad email, but the page showed nonsense. Only a browser test could catch this: the API test passed.

Before: the error box on the login page 
[object Object]
After: api/client.js formats FastAPI's error list 
email: value is not a valid email address
BUG-023LowFixed

A test that only failed after 6 pm

The app used the server's local clock for “today”; PostgreSQL uses UTC. In the evening (US Central time) they were already on different days, so a new rate table did not apply until the next morning.

Before: 10:25 pm on 11 November 
Python  date.today()   -> 2026-11-11
Postgres CURRENT_DATE  -> 2026-11-12
After: app/clock.py, used everywhere 
def today():
    return datetime.now(timezone.utc).date()

BUG-001CriticalSecurity
Before

No endpoint except /me required a login. Anyone could read every customer's name, birth date, licence number and phone with a plain HTTP request.

Fix

Every data router now declares Depends(get_current_account). No token returns 401.

routers/*.py

New require_admin and customer_scope checks. Customers see only their own record, vehicles, policies and claims; creating policyholders and the company dashboard are admin-only (403).

What testing taught us

Not every failing test meant the app was broken. We investigated each surprise before deciding what to fix: the app, the test, or the environment.

  1. The test was wrong, not the app

    Two of our first expected values were worked out wrong by hand: a risk-level check forgot the power factor, and a Region B price assumed Region A's 1.05 power factor instead of 1.04. The app's $351.41 was correct. Expected values must come from the data, never be copied between cases.

  2. Fixing a bug changed the requirements

    After BUG-010, a 0 kW engine became an invalid input, so two old unit tests that priced a 0 kW car failed. We updated them: when a rule changes, its tests change too.

  3. Flaky test, cause 1: a database deadlock

    A browser test could finish while its last API request was still running. The next test's database reset then deadlocked with it, and later tests started from the wrong data. We now reset with one TRUNCATE and retry if Postgres reports a deadlock.

  4. Flaky test, cause 2: the runtime crashed

    About 2 runs in 10 lost the frontend server mid-run. Node.js exited with code 0xC0000409, a native crash, while the build output sat in a OneDrive-synced folder. We moved the build to a temp folder, isolated the server process and added an automatic restart.

To make sure the suite is reliable, we ran the browser tests 10 times in a row after the last change. All 10 runs passed, all 35 tests each time.

Known limitations

  • Login token in localStorage. Acceptable for a class project. A production app would use an HttpOnly cookie.
  • Login throttling is kept in memory. Fine on one server; several servers would need a shared store such as Redis.
  • Vehicle age is validated but not priced. Whether newer or older cars should cost more is a business decision we have left open.
  • Customers see “Admin access required” on the dashboard. Its figures are company-wide; a customer dashboard is future work.
